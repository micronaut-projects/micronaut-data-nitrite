Micronaut Data Nitrite

Micronaut Data support for the Nitrite embedded document database

Version: 5.2.0-SNAPSHOT

1 Overview

Micronaut Data Nitrite is an embedded, document-oriented datastore implementation backed by NitriteDB.

It supports common Micronaut Data repository patterns, including:

  • Repositories

  • Configuration

  • Entity Mapping

  • Association Fetching

  • Criteria API

  • Jakarta Data repository query semantics for common document queries

  • Transactions (via Micronaut Data TX infrastructure)

  • Spatial Queries

Nitrite is intended for practical embedded use-cases that need Micronaut Data repositories without running an external datastore. It supports the core repository, mapping, association, criteria, projection, sorting, pagination, transaction, optimistic locking, and optional spatial features described in this chapter. It is not a feature-equivalent MongoDB replacement; see Scope and Limitations.

2 Quick Start

Micronaut Launch does not currently offer a dedicated data-nitrite feature. The quickest way to get started is to add the Nitrite implementation and the Micronaut Data annotation processors to an existing Micronaut application.

Dependency Setup

Add the following dependencies to your annotation processor path:

annotationProcessor("io.micronaut.data:micronaut-data-document-processor")
<annotationProcessorPaths>
    <path>
        <groupId>io.micronaut.data</groupId>
        <artifactId>micronaut-data-document-processor</artifactId>
    </path>
</annotationProcessorPaths>
[tool.pyronaut.dependencies]
build = [
    "io.micronaut.data:micronaut-data-document-processor",
]

annotationProcessor("io.micronaut.data:micronaut-data-nitrite-core")
<annotationProcessorPaths>
    <path>
        <groupId>io.micronaut.data</groupId>
        <artifactId>micronaut-data-nitrite-core</artifactId>
    </path>
</annotationProcessorPaths>
[tool.pyronaut.dependencies]
build = [
    "io.micronaut.data:micronaut-data-nitrite-core",
]

For Kotlin, add both dependencies to the kapt or ksp configuration, and for Groovy add both in compileOnly scope.

micronaut-data-nitrite-core is needed on the annotation processor path: it carries the NitriteQueryBuilder that @NitriteRepository names, and Micronaut Data resolves that builder at compilation time. Without it, repository methods are compiled against the default JPQL query builder instead of into Nitrite filters, and Nitrite-specific features such as projections, association lookups and $regex queries are lost.

Then add a compile-scoped dependency on the Nitrite implementation:

implementation("io.micronaut.data:micronaut-data-nitrite")
<dependency>
    <groupId>io.micronaut.data</groupId>
    <artifactId>micronaut-data-nitrite</artifactId>
</dependency>
[tool.pyronaut.dependencies]
runtime = [
    "io.micronaut.data:micronaut-data-nitrite",
]

Saving an Instance (Create)

To save an instance use the save method of the CrudRepository interface:

Book book = new Book("The Stand");
bookRepository.save(book);
val book = bookRepository.save(Book(title = "The Stand"))
def book = bookRepository.save(new Book("The Stand"))

The save method inserts or updates according to what the collection holds:

  • If the entity’s ID is null, a new document is inserted and the ID is generated

  • If the entity’s ID is present in the collection, that document is replaced

  • If the entity’s ID is not present in the collection, a new document is inserted under it

This means save() can be used for both creating new entities and updating existing ones, including entities whose ID the application assigns itself.

Retrieving an Instance (Read)

To read an entity back use findById:

Book found = bookRepository.findById(book.getId()).orElseThrow();
val found = bookRepository.findById(book.id!!).orElseThrow()
def found = bookRepository.findById(book.id).orElse(null)

Updating an Instance (Update)

Nitrite updates are executed via explicit update methods (for example, update by ID):

void update(@Id String id, String title);
fun update(@Id id: String, title: String)
void update(@Id String id, String title)

Which can then be called like so:

bookRepository.update(book.getId(), "Changed");
bookRepository.update(book.id!!, "Changed")
bookRepository.update(book.id, "Changed")

Deleting an Instance (Delete)

To delete an instance use deleteById:

bookRepository.deleteById(book.getId());
bookRepository.deleteById(book.id!!)
bookRepository.deleteById(book.id)

3 Configuration

Configuration

Nitrite datasources are bound from micronaut.nitrite. properties. Each datasource has a name, which forms part of the property path: settings for a datasource named default are bound from micronaut.nitrite.default..

The following settings are supported for each datasource:

  • db-path: Path to the database file. MVSTORE without a path uses pure in-memory storage; ROCKSDB requires a path. IN_MEMORY ignores the path.

  • storage-mode: The storage engine to use. Supported values are:

    • MVSTORE: (Default) MVStore-backed persistent database.

    • IN_MEMORY: Pure in-memory database (equivalent to leaving db-path empty).

    • ROCKSDB: RocksDB-backed persistent database.

  • field-separator: The character used to separate nested fields in query strings (default: .).

  • create-indexes: Whether to automatically create indexes from Micronaut Data @Index, @Indexes, @FullTextIndex, and @SpatialIndex annotations (default: true).

  • sorted-read-strategy: How limits are applied to sorted reads (default: AUTO):

    • AUTO: Uses cursor-side limits for MVSTORE and in-memory storage, and database-side limits for ROCKSDB.

    • CURSOR: Always removes the limit from the Nitrite find and applies it while reading the cursor.

    • DATABASE: Always keeps the limit on the Nitrite find.

  • mvstore-page-split-size: The MVStore page split size in bytes. Unset by default, which leaves the Nitrite adapter’s own value in place. Only read when storage-mode is MVSTORE.

    Nitrite 5.4.0 defaults to 16 KB (16384 bytes). The explicit 16384 workaround for Nitrite 5.3.0 is no longer needed; an existing override remains valid. H2 clamps the value to (cacheSize / cacheConcurrency) >> 4. Existing pages keep their shape until rewritten.

The remaining MVStore settings are unset by default and, like the one above, are read only for MVSTORE. An unset value leaves the adapter’s own default in place:

  • mvstore-retention-time: Chunk retention time in milliseconds. Unset preserves H2’s default of 45 seconds. Space reclamation waits for this window; close still compacts synchronously.

  • mvstore-versions-to-keep: Number of old versions retained. Unset preserves H2’s default of five. Setting both retention and versions-to-keep to zero restores the earlier behaviour that can leave an unreadable store.

  • mvstore-allowed-classes: Additional semicolon-separated JEP 290 patterns for application classes stored as Java serialized values, for example com.example.model.. Nitrite 5.4.0 allows Nitrite and JDK classes by default. The spatial integration adds org.locationtech.jts.geom. when installed; application classes attached as geometry user data still need their own patterns. A process-wide jdk.serialFilter can still reject classes allowed here.

  • mvstore-cache-size: Read cache size in MB (adapter default: 16).

  • mvstore-cache-concurrency: Number of read cache segments (adapter default: 16). H2 clamps the page split size to (cacheSize / cacheConcurrency) >> 4, so this bounds mvstore-page-split-size.

  • mvstore-auto-commit: Whether every change is committed as it is made (adapter default: true). With this off, changes are buffered until Nitrite.commit().

  • mvstore-auto-commit-buffer-size: Unsaved changes buffered before an automatic commit (adapter default: 1024). Only meaningful while auto-commit is on.

  • mvstore-auto-compact: Whether fragmented chunks and chunks below the 90% target fill rate are reclaimed, which shrinks the file (adapter default: true).

  • mvstore-compress: Whether stored data is compressed (adapter default: false).

  • mvstore-compress-high: Whether the higher compression level is used - smaller file, slower reads and writes (adapter default: false).

  • mvstore-recovery-mode: Whether the store opens in MVStore’s recovery mode, which tolerates a file H2 would otherwise refuse (adapter default: false).

  • mvstore-read-only: Whether the store opens read-only (adapter default: false).

  • mvstore-encryption-key: The key MVStore encrypts the file with. Unset means an unencrypted store. Supply it from the environment rather than checked-in configuration. Encryption is an MVStore feature; the RocksDB adapter has no equivalent.

  • username: Optional username (for authenticated databases).

  • password: Optional password.

Example (Persistent):

micronaut:
  nitrite:
    default:
      db-path: /data/myapp.db
      create-indexes: true

If no micronaut.nitrite configuration is present at all, an in-memory datasource named default is created implicitly, so a repository works without any configuration. A configured MVSTORE datasource without a db-path also uses in-memory storage. ROCKSDB always requires a path.

Backend Builder Customization

For settings that require Java objects, register a Micronaut bean implementing MvStoreModuleCustomizer from micronaut-data-nitrite-mvstore or RocksDbModuleCustomizer from micronaut-data-nitrite-rocksdb. The customizer receives the datasource configuration and its fresh upstream builder before the module is built. It runs only for a persistent datasource using that backend; MVSTORE without a path uses pure in-memory storage.

Customizers run after datasource properties, in ascending getOrder() order (default: zero). Use distinct orders when customizers set the same option; later customizers override earlier ones. Each bean is invoked for every datasource of its backend. Check configuration.getName() to restrict it to one datasource:

import io.micronaut.data.nitrite.conf.NitriteConfiguration;
import io.micronaut.data.nitrite.mvstore.MvStoreModuleCustomizer;
import jakarta.inject.Singleton;
import org.dizitart.no2.mvstore.MVStoreModuleBuilder;

@Singleton
class AuditMvStoreCustomizer implements MvStoreModuleCustomizer {
    @Override
    public void customize(NitriteConfiguration configuration, MVStoreModuleBuilder builder) {
        if ("audit".equals(configuration.getName())) {
            builder.autoCommitBufferSize(4096);
        }
    }
}

The MVStore hook exposes the entire upstream builder, including fileStore and store event listeners. The RocksDB hook exposes Options, DBOptions, ColumnFamilyOptions, custom object formatters and store event listeners. Keep supplied resources alive until the database closes; RocksDB closes the native options it uses, so create a fresh set for each datasource rather than sharing native options across databases. Customizing the deserialization patterns replaces the patterns assembled from datasource properties and spatial support, so preserve the geometry patterns when using spatial values.

Nitrite 5.4.0 Upgrade Behaviour

Custom Java serialized document values require the mvstore-allowed-classes setting when read from an MVStore file. Normal entity properties mapped to documents, maps and JDK values do not need an application allowlist. Values passed through without conversion, including values from custom converters or direct Nitrite collection access, may need one. In native applications, allowlisting does not register a class for Java serialization: custom values also require the corresponding GraalVM serialization metadata.

Unique indexes migrate from lists of IDs to a single-ID layout on first access. Back up a database before upgrading if it may need to be opened by an earlier Nitrite release.

find() and getById() return structurally copied documents. Change stored data through explicit updates; mutating a returned list, map, array, date or calendar does not persist a change. Unknown mutable value types, including JTS geometries, can still be shared. Update a geometry through a repository operation instead of mutating its coordinates in place. Each result and write now pays for the structural copy.

Multiple Datasources

More than one datasource can be configured by giving each one its own name under micronaut.nitrite. Each datasource is opened independently, with its own storage mode and its own documents:

micronaut:
  nitrite:
    default:
      db-path: /data/myapp.db
    audit:
      storage-mode: IN_MEMORY

A repository selects its datasource by passing the name to @NitriteRepository:

@NitriteRepository("audit")
public interface AuditRepository extends CrudRepository<AuditRecord, String> {
}

A repository that names no datasource uses the primary one, which is the datasource named default.

Datasources are isolated from each other: an entity written through a repository bound to one datasource is not visible through a repository bound to another, even when both repositories map the same entity type.

The isolation extends to transactions. Each datasource gets its own connection operations, transaction operations and transaction context holder, so a transaction opened against one datasource neither covers nor is visible to repositories bound to another. To drive a transaction of a named datasource programmatically, resolve its NitriteTransactionOperations bean by that name:

NitriteTransactionOperations auditTransactions =
    beanContext.getBean(NitriteTransactionOperations.class, Qualifiers.byName("audit"));

The spatial module enables:

  • Spatial indexes on Geometry fields

  • Spatial filters ($near, $within, $intersects)

With Nitrite 5.4.1, spatial-index queries on a reopened MVStore file can fail with ClassCastException (DefaultSpatial to MVSpatialKey) inside the upstream adapter. Geometry values themselves can be read after reopening. Persistent spatial-index queries on MVStore require an adapter release containing the persisted-key fix; the in-memory spatial verification does not cover that case. When verifying an adapter containing the fix, add -PverifySpatialIndexReopen=true to the dedicated JVM or native verification command to exercise persisted spatial queries, updates and deletes. This regression is opt-in while the BOM pins the affected 5.4.1 release.

The module is loaded automatically when it is on the classpath and is simply absent when it is not. A module that is present but cannot be initialized fails at startup rather than being skipped, so spatial indexes and filters are never silently unavailable.

See Spatial Queries for detailed usage. See the Nitrite Spatial Module documentation and Spatial Filters documentation for more details.

Object Mapping

Micronaut Data Nitrite uses its own Micronaut Data mapping layer with Nitrite collections. It does not require Nitrite’s Jackson mapper module, and a Micronaut Serde ObjectMapper bean is optional. If Micronaut Serde is present, the mapper can use it for non-simple nested values; otherwise it relies on Micronaut introspection and the built-in conversion service.

Batch Operations

For bulk operations, use the saveAll, updateAll, and deleteAll repository methods:

    void batchOperations() {
        java.util.List<Book> books = java.util.List.of(
            new Book("Book 1"),
            new Book("Book 2"),
            new Book("Book 3")
        );
        bookRepository.saveAll(books); // Single batch operation
    }
    fun batchOperations() {
        val books = listOf(
            Book("Book 1"),
            Book("Book 2"),
            Book("Book 3")
        )
        bookRepository.saveAll(books) // Single batch operation
    }
    void batchOperations() {
        def books = [
            new Book("Book 1"),
            new Book("Book 2"),
            new Book("Book 3")
        ]
        bookRepository.saveAll(books) // Single batch operation
    }

The insert portion of saveAll is submitted as a batch; updates and entity-based deletes are applied per document. Nitrite is embedded, so these operations do not involve network round-trips. To commit or roll back several changes together, run them in a transaction; see Transactions.

For large batch operations, consider breaking them into smaller chunks to avoid memory pressure and improve transaction management.

As seen in the Quick Start repositories are defined using the @NitriteRepository stereotype annotation.

}

}

Micronaut Data generates an implementation at compile time and executes queries via the Nitrite runtime implementation.

A repository that names no datasource uses the primary one. To bind a repository to a particular datasource, pass its name to the annotation, for example @NitriteRepository("audit"). See Configuration for configuring more than one datasource.

You can use standard repository method patterns:

  • CRUD methods from CrudRepository

  • Derived finders (for example findByTitle, findByAgeGreaterThan, existsBySku)

  • Paging and sorting via Pageable and Sort

  • Case-insensitive queries (for example findByTitleIgnoreCase)

  • IN queries with collections and arrays (for example findByTitleIn)

CRUD Semantics

The write methods follow the Jakarta Data lifecycle contract.

save() and saveAll() are conditional. They decide between an insert and an update from what the collection holds, not from whether the entity carries an identity:

  • If the entity’s ID is null, a new document is inserted and the ID is generated

  • If the entity’s ID is present in the collection, that document is replaced

  • If the entity’s ID is not present in the collection, a new document is inserted under it

An assigned identity - UUID, String, an application-set Long - is therefore inserted on its first save and updated on every later one, and saveAll() may insert some of its batch and update the rest.

insert(), update() and their batch forms are unconditional, for every entity, versioned or not:

  • insert() and insertAll() reject an identity the collection already holds with EntityExistsException

  • update(), updateAll(), delete() and deleteAll() require the document to exist: an entity whose ID matches nothing raises OptimisticLockException rather than being inserted or silently affecting nothing

  • An entity with no ID at all is never inserted by update(); it reports zero affected rows

Case-Insensitive Queries

Nitrite supports case-insensitive queries using the IgnoreCase suffix in method names:

    // Case-insensitive search by title
    List<Book> findByTitleIgnoreCase(String title);

    // Case-insensitive contains
    List<Book> findByTitleContainsIgnoreCase(String keyword);
    // Case-insensitive search by title
    fun findByTitleIgnoreCase(title: String): List<Book>

    // Case-insensitive contains
    fun findByTitleContainsIgnoreCase(keyword: String): List<Book>
    // Case-insensitive search by title
    List<Book> findByTitleIgnoreCase(String title)

    // Case-insensitive contains
    List<Book> findByTitleContainsIgnoreCase(String keyword)

IN Queries

Nitrite supports IN queries with both collections and arrays:

    // IN query with List parameter
    List<Book> findByTitleIn(List<String> titles);

    // IN query with array parameter
    List<Book> findByTitleIn(String[] titles);

    // NOT IN query
    List<Book> findByTitleNotIn(List<String> titles);
    // IN query with List parameter
    fun findByTitleIn(titles: List<String>): List<Book>

    // IN query with array parameter
    fun findByTitleIn(titles: Array<String>): List<Book>

    // NOT IN query
    fun findByTitleNotIn(titles: List<String>): List<Book>
    // IN query with List parameter
    List<Book> findByTitleIn(List<String> titles)

    // IN query with array parameter
    List<Book> findByTitleIn(String[] titles)

    // NOT IN query
    List<Book> findByTitleNotIn(List<String> titles)

Field Projections

Nitrite supports single-field projections and aggregate functions, including property-scoped distinct counts:

    // Single-field projection - returns List<String>
    List<String> findDistinctTitle();

    // Count query - returns long
    long countByAuthorId(String authorId);

    // Aggregate functions
    Long countByTitle(String title);
    // Count query - returns long
    fun countByAuthorId(authorId: String): Long

    // Aggregate functions
    fun countByTitle(title: String): Long?
    // Single-field projection - returns List<String>
    List<String> findDistinctTitle()

    // Count query - returns long
    long countByAuthorId(String authorId)

    // Aggregate functions
    Long countByTitle(String title)

For example, methods such as findDistinctTitle(), countByAuthorId(…​), and countByTitle(…​) are resolved by the Nitrite runtime without requiring a native Nitrite aggregation pipeline. DTO Projections

Micronaut Data Nitrite supports reflection-free DTO projections for repository methods that return a type other than the root entity. The DTO must be a concrete class (or record/data class) annotated with @Introspected, with a constructor or getter/setter pair for every projected property. Unlike JDBC/JPA, only concrete DTO types work: an @Introspected interface compiles but fails at runtime, because the Nitrite mapper instantiates the DTO via its BeanIntrospection constructor, and interfaces have none.

5.2 Automated Index Creation

Automated Index Creation

Micronaut Data Nitrite automatically creates indexes based on standard Micronaut Data annotations.

You can define indexes at the class level or property level using @Index or @Indexes.

Identity Indexing and Uniqueness

A Long identity is written into Nitrite’s own _id document key as well as into the id field, so its lookups are already a single key seek and its uniqueness is already enforced by that key. No secondary index is created for it: measured over the benchmark suite, one cost 29.8% of transactional write throughput on MVStore, 19.5% in memory, and 26.0% of association reads.

Every other scalar identity - String, UUID, Integer and the rest - cannot be held in _id, so Micronaut Data Nitrite creates a unique index on the id field instead. That index is what makes an identity lookup seekable and what raises EntityExistsException when insert is given an identity that already exists.

Composite, embedded and association identities are given no identity index.

Applying @Index to a property creates a non-unique index on that field:

Indexes and Sorting

When a query has no filter, orders by exactly one field, and asks for a bounded number of records, Nitrite takes the ordering from a simple index on that field rather than blocking-sorting the collection. That path is slower than the sort it replaces: measured against Nitrite 5.3.0 it cost about 3.4 times a blocking sort at every collection size and every bound tried, and its cost grows with the size of the collection rather than with the number of records asked for.

A sorted read is therefore issued unbounded and bounded while its cursor is read, whether the bound comes from a Pageable page size, from a Limit, or from returning a single result. A skip does not select the index path and is left with the find, so only a suffix of the cursor is ever dropped. Ordering, null placement and tie-breaking are unaffected.

The default AUTO strategy uses this cursor-side behavior for MVSTORE and in-memory storage. It keeps the bound on the Nitrite find for ROCKSDB, whose bounded indexed path is faster in the benchmark. Set sorted-read-strategy to CURSOR or DATABASE to force one strategy for all storage modes; see Configuration.

For a single-result read this changes nothing a caller can observe: a Top/First query returns the first record, and any other single-result query still reads a second record to detect a non-unique result and raises NonUniqueResultException rather than silently returning the first.

Managing Indexes Directly

A NitriteIndexManagement bean is created for each datasource. It drops and rebuilds a unique index on a named collection field, and dropUniqueIndex returns a closeable scope that rebuilds the index when the scope closes, so a bulk load can run unindexed without leaving the collection unindexed if it fails. Index DDL is not part of a Nitrite transaction, so this is the only way to undo a drop.

Configuration

Automatic index creation, including the identity index, can be disabled by setting create-indexes to false for the datasource, for example micronaut.nitrite.default.create-indexes. Without the identity index a duplicate non-Long identity is no longer rejected by the database, so insert of an entity whose identity already exists writes a second document rather than raising EntityExistsException.

Composite Primary Keys

Composite primary keys can be defined using @EmbeddedId.

A composite ID requires an additional class to represent the key. The class should define fields that correspond to the attributes making up the key.

Multiple @Id Properties

An identity can also be composed by annotating more than one property with @Id, without a separate key class. Each identity property is stored as a document field of its own, so it round-trips with the entity and can be filtered and sorted on like any other property. The identity properties are also appended to the sort of a paged query, giving a page boundary a tie-breaker when the requested sort is on a non-unique field.

5.5 Naming Strategies

Naming Strategies

The default naming strategy when converting camel case class and property names to collection and attribute names is to use underscore separated lower case (snake_case). In other words FooBar becomes foo_bar.

This naming strategy applies to:

  • Entity class names (converted to collection names)

  • Entity property names (converted to document field names)

  • Aggregation query field references

Date/Time Serialization

Date and time types are normalized before being stored in Nitrite documents so filtering, sorting, and aggregation use stable representations. For example:

  • LocalDate is stored as an epoch-day number.

  • Instant and LocalDateTime are stored as epoch-nanosecond numbers.

  • OffsetDateTime and ZonedDateTime are stored as ISO-8601 offset strings.

The runtime applies the same normalization to query parameters, so repository methods can continue to use Java time types directly.

@Query JSON Filters

When using the @Query annotation with explicit JSON filter documents, field names use snake_case format to match the stored document structure. For example, a property firstName is stored as first_name in the document.

The framework automatically converts camelCase property names to their snake_case persisted names when processing @Query JSON filters:

{"firstName": "John"}  // Converted to {"first_name": "John"} internally

This means developers can use either camelCase or snake_case in @Query JSON filters - both will work correctly.

5.6 Association Mapping

To specify a relation between two entities, use the @Relation annotation. The relation kind is specified using the enum Relation.Kind value attribute, which is similar to JPA relationship annotations (@OneToMany, @OneToOne, etc.).

Supported Relation Types

Table 1. Micronaut Data Nitrite supported relations:

Kind

Description

Kind.ONE_TO_MANY

One-To-Many association. The associated entities are stored in a separate collection with a foreign key reference back to the owning entity.

Kind.ONE_TO_ONE

One-To-One association. The associated entity is referenced by ID in the owning document.

Kind.MANY_TO_MANY

Many-To-Many association. Both entities maintain collections of the other, stored with foreign key references.

Kind.MANY_TO_ONE

Many-To-One association. The owning entity stores the ID of the associated entity as a foreign key.

Kind.EMBEDDED

Embedded association. The associated entity’s fields are stored inline within the owning document.

Use the mappedBy attribute to specify the inverse property that this relation is mapped by. This is required for bidirectional associations.

Cascade Operations

Micronaut Data Nitrite supports cascading operations on associations. The cascade type is specified using the cascade attribute of the @Relation annotation.

Table 2. Micronaut Data Nitrite supported cascade types:

Type

Description

Cascade.PERSIST

Associated entity or entities are automatically persisted when the owning entity is saved.

Cascade.UPDATE

Associated entity or entities are automatically updated when the owning entity is updated.

Cascade.ALL

All operations (Cascade.PERSIST and Cascade.UPDATE) are cascaded to associated entities.

Cascade.NONE

(Default) No operations are cascaded. Associated entities must be managed explicitly.

6 Association Fetching

Micronaut Data Nitrite supports fetching of associations using the @Join annotation. This allows you to eagerly load related entities when querying.

Supported Association Types

Nitrite supports the following association types with @Join:

  • Kind.ONE_TO_ONE - Single-valued association

  • Kind.MANY_TO_ONE - Single-valued association

  • Kind.ONE_TO_MANY - Collection-valued association

  • Kind.MANY_TO_MANY - Collection-valued association

Using @Join

To fetch associations eagerly, use the @Join annotation on repository methods:

@NitriteRepository
public interface AuthorRepository extends CrudRepository<Author, String> {

    // Fetch books when finding by ID
    @Join("books")
    Optional<Author> findById(String id);

    // Fetch books when searching by name
    @Join("books")
    Author searchByName(String name);

    // Fetch all authors with their books eagerly loaded
    @Join("books")
    List<Author> findAll();

    // Find authors by their book's title (reverse lookup on ONE_TO_MANY)
    Optional<Author> findByBooksTitle(String title);
}

Lazy by Default

ONE_TO_MANY and MANY_TO_MANY associations are lazy-loaded by default in Nitrite. This means:

  • Without @Join: the collection is not loaded (empty)

  • With @Join: the collection is fetched in the same query operation, using a single batch query rather than one query per entity

MANY_TO_ONE and ONE_TO_ONE associations, by contrast, are always eagerly resolved — the owning entity stores the foreign key directly, so Nitrite fetches the associated entity whether or not @Join is used. Adding @Join to these still helps: it replaces the per-entity lookup with a single $lookup-based query, and is required to filter or project through the association with the Criteria API.

Without @Join, each to-one association is resolved with a separate lookup per root document, and the associated entity’s own to-one associations are resolved in turn. Loading N entities therefore costs N additional lookups per to-one association, and can walk further into the graph from there. Each root document has its own hydration cache, so the same associated document is fetched again for every root that references it, and cycles are handled without infinite recursion. Declare @Join on the association when loading more than a handful of entities, and model deep to-one chains deliberately.

The @Join annotation triggers a batch fetch that:

  1. Queries all Author entities

  2. Collects all author IDs

  3. Queries all Book entities where author_id IN (author IDs)

  4. Groups books by author ID

  5. Populates each author’s books collection

Fetching MANY_TO_MANY Associations

For MANY_TO_MANY associations, @Join works the same way as ONE_TO_MANY. The owning side stores the relationship, and Nitrite can resolve the association when fetching from either side.

In the Student/Book example, Book is the owning side (it has @Relation(value = Relation.Kind.MANY_TO_MANY) without mappedBy), while Student is the inverse side (it has mappedBy = "students").

To eagerly fetch students when querying books, add @Join("students") to a findAll method on BookRepository:

    // Eagerly fetch students for all books (MANY_TO_MANY)

    List<Book> findAll()

The @Join annotation triggers a batch fetch that:

  1. Queries all Book entities

  2. For each book, reads the stored student ID references from the owning side’s field

  3. Queries all Student entities whose IDs are in the collected set

  4. Groups students by book ID

  5. Populates each book’s students collection

  • Students collection is already populated, no additional queries

Batch Fetching

When multiple entities are loaded with @Join, Nitrite uses batch fetching to efficiently load associations:

  1. Load all parent entities

  2. Collect parent IDs

  3. Query associated entities with IN clause

  4. Group results by parent ID

  5. Populate associations on parent entities

This approach minimizes database queries and is efficient for loading collections.

Limitations

Current boundaries of @Join support in Nitrite:

  • Use explicit @Join annotations for each association path that should be fetched.

  • Nested association paths are supported by declaring each path explicitly, for example @Join("books") and @Join("books.pages").

  • Deep nested graphs should be modeled deliberately; avoid relying on broad implicit graph loading.

  • Only the default join behavior is supported; custom join types such as LEFT_FETCH and INNER_FETCH are not currently distinguished.

Association Name Matching

Nitrite uses the associated entity’s class name for matching association paths in queries. This handles both regular and irregular plural forms correctly:

  • Regular plurals: books → book (e.g., findByBooksTitle)

  • Irregular plurals: cities → city (e.g., findByCitiesName)

This ensures that queries on ONE_TO_MANY associations work correctly regardless of the naming convention used.

7 Optimistic Locking

Optimistic locking is a strategy where you note the actual record state’s version and modify the record only when the version is the same.

To enable optimistic locking for your entity, add a field annotated with @Version with one of the following types:

  • java.lang.Integer

  • java.lang.Long

  • java.lang.Short

  • Date-time types extending java.time.Temporal (e.g., Instant, LocalDateTime)

The version field is automatically initialized to 0 for numeric types or to the current timestamp for temporal types. It is incremented (for numeric types) or replaced (for temporal types) on each update operation.

Micronaut Data Nitrite includes the current version in update and delete filter queries. If no matching document is found (because the version has changed), an OptimisticLockException is thrown.

8 Transactions

Transactions

Nitrite integrates with Micronaut’s @Transactional infrastructure through NitriteTransactionOperations. When a transaction is active, repository calls participate in the same Nitrite transaction and are committed or rolled back together, whichever storage engine backs the datasource. Keep units of work short to avoid blocking other threads that need to mutate the store.

Transaction and connection operations exist once per configured datasource. A transaction therefore covers exactly the datasource it was opened against; see Multiple Datasources.

To select a named datasource’s NitriteTransactionOperations or NitriteConnectionOperations, use a @Named qualifier naming that datasource. The default datasource remains the primary one and resolves without a qualifier.

Examples

Transactional method using @Transactional annotation:

  bookRepository.save(new Book(title));
}
@Transactional

  bookRepository.save(Book(title))
}
@Transactional

  bookRepository.save(new Book(title))
}

Rollback control

If you need to mark the current transaction rollback-only after some condition, use the TransactionOperations helper (executeWrite/executeRead) to set the status without throwing an exception.

Entity Events

Nitrite supports entity lifecycle events (see Entity Events). Event callbacks such as @PrePersist, @PostPersist, @PreUpdate, @PostUpdate, @PreRemove, and @PostRemove are triggered during transactional operations.

When cascade operations are used, child entity events are triggered before parent entity events (children before parent for cascade operations).

Predicate and Expression Support

Nitrite supports the common Micronaut Data and Jakarta Data predicate set for document repositories, including:

  • equality and inequality

  • comparison operators (greaterThan, greaterThanOrEqualTo, lessThan, lessThanOrEqualTo)

  • between

  • in and not in, including empty collections

  • isNull, isNotNull, isTrue, isFalse, empty and not-empty string checks

Computed expression predicates are evaluated by the Nitrite runtime against candidate documents when Nitrite has no equivalent native indexed operator. Association Queries

Nitrite supports Criteria queries on associations:

  • MANY_TO_ONE: Filter by association properties using PredicateSpecification

  • ONE_TO_MANY: Reverse lookups through method names or specifications

Filtering by MANY_TO_ONE Associations

You can use the Criteria API to navigate associations in PredicateSpecification:

        criteriaBuilder.equal(root.get("author").get("name"), name);
}

        criteriaBuilder.equal(root.get('author').get('name'), name)
    } as PredicateSpecification<Book>
}

This example filters books by their author’s name using root.get("author").get("name"). Nitrite automatically:

  1. Builds a sub-query on the author collection

  2. Finds matching author IDs

  3. Filters books by the author_id foreign key

The author field in Book must be annotated with @Relation(Relation.Kind.MANY_TO_ONE) for this to work.

Reverse Lookups on ONE_TO_MANY Associations

For reverse lookups on ONE_TO_MANY associations, the query builder preserves the property path and Nitrite executes a sub-query to find matching parent entities.

Example of a reverse lookup method:

    // Find authors by their book's title (reverse lookup on ONE_TO_MANY)
    Optional<Author> findByBooksTitle(String title);
    // Find authors by their book's title (reverse lookup on ONE_TO_MANY)
    fun findByBooksTitle(title: String): Author?
    // Find authors by their book's title (reverse lookup on ONE_TO_MANY)
    Author findByBooksTitle(String title)

The above method finds authors who have written a book with the specified title. Internally, Nitrite:

  1. Queries the book collection for documents where title matches the parameter

  2. Collects the author_id foreign keys from matching books

  3. Queries the author collection for documents with matching IDs

This approach allows natural property-path queries while efficiently handling the reverse lookup through the foreign key relationship.

Reverse lookups on ONE_TO_MANY associations require that the child entity (e.g., Book) has a foreign key reference to the parent entity (e.g., Author). The @Relation annotation with Kind.MANY_TO_ONE on the child entity establishes this relationship.

Query Format

Nitrite-specific notes:

  • Parameters are bound positionally using placeholders of the form "$mn_qp:<index>".

  • Temporal query parameters are normalized to match Nitrite’s stored representation. For example, Instant and LocalDateTime values are compared using epoch-nanosecond values.

  • Numeric equality comparisons are tolerant to representation differences introduced by the mapping layer (for example Long vs BigDecimal).

  • Date/time field names use snake_case format in aggregation queries (e.g., last_updated).

11 Scope and Limitations

Scope and Current Boundaries

Nitrite is intended as an embedded datastore for Micronaut Data repository applications. It now supports more than basic CRUD, including criteria queries, association mapping and fetching, optimistic locking, transactions, lifecycle events, and optional spatial queries.

It is still a Nitrite-backed embedded store, not a MongoDB compatibility layer. In particular:

  • Nitrite is not a BSON/driver-native query-document store like MongoDB.

  • MongoDB-specific features such as aggregation pipelines, BSON filters, and Mongo-only annotations are out of scope for this module.

  • Persistent storage engines other than the default MVStore (for example, RocksDB) require the corresponding Micronaut Nitrite integration dependencies in your build configuration.

  • If you need full MongoDB feature parity, use Micronaut Data MongoDB instead (see Micronaut Data MongoDB).

Feature Overview

Micronaut Data Nitrite supports the following features for embedded document storage:

  • Repository patterns with derived query methods

  • Criteria API with sorting, pagination, projection, logical predicates, LIKE/regex matching, and common computed expressions

  • Association mapping with cascade operations

  • Association fetching with @Join annotation

  • Optimistic locking with @Version annotation

  • Transaction management with programmatic transactions

  • Multiple datasources, each with its own storage mode

  • Spatial queries with Geometry types (requires spatial module)

  • Entity lifecycle events (see Shared Entity Events)

For details and examples, see the respective sections above.

Remaining Limitations

The following boundaries remain:

  • Spatial-index operations after reopening an MVStore file require a corrected upstream adapter; released Nitrite 5.4.1 still has the persisted-key cast failure described in Configuration.

  • @Join uses Nitrite’s default fetch behavior; custom join types such as LEFT_FETCH and INNER_FETCH are not currently distinguished.

  • Criteria subqueries (cb.exists(subquery)) are not supported by Nitrite.

  • Criteria sum, diff, and unsupported string transforms such as trim are rejected in query expressions. Supported computed expressions such as length, lower, upper, concat, right, and prod are evaluated in application code against candidate documents rather than pushed down to Nitrite indexes, so use them with care on large collections. This applies only to computed expressions: a plain comparison on a field, including >, >=, <, ⇐ and between, is expressed as a native Nitrite filter and can be served by an index on that field.

  • A criteria update assigns values only. CriteriaUpdate.set accepts a value or a parameter, not a computed expression such as cb.sum(path, 1), cb.quot(path, 2) or cb.concat(path, suffix), which Micronaut Data rejects for every implementation. To apply a computed update, read the entity, change it and save it, or use a @Query update with $inc, $mul or $concat.

  • Nitrite has no derived update operators of its own, so $inc, $mul and $concat are applied by reading each matching document, computing the new value and writing it back. The sequence is serialized per collection so that concurrent updates are not lost, which means arithmetic updates on the same collection do not proceed in parallel. A result that does not fit the stored field’s type — an overflowing increment on an Integer field, for example — fails with an DataAccessException rather than wrapping silently.

  • Advanced Mongo-style aggregation pipelines are out of scope. Use repository aggregate methods, including property-scoped distinct counts, and Criteria API support where applicable.

  • Embedded/nested POJO values are persisted and round-trip correctly, but derived nested-property queries against arbitrary embedded object fields depend on annotation processor support.

  • Immutable entities are not supported. An entity is populated through its setters on both the write and the read side, so a Java record, or any entity whose identity is read-only, fails with Cannot write a read-only property. A generated identity is assigned in place before the insert, and a document is mapped back into a new instance the same way. An immutable entity whose identity is assigned by the application can be written, and the instance returned by save does carry its initial version, but it cannot be read back.
