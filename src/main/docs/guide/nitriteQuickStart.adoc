[[nitriteQuickStart]]
Micronaut Launch does not currently offer a dedicated `data-nitrite` feature. The quickest way to get started is to add the Nitrite implementation and the Micronaut Data annotation processors to an existing Micronaut application.

== Dependency Setup

Add the following dependencies to your annotation processor path:

dependency:io.micronaut.data:micronaut-data-document-processor[scope="annotationProcessor"]

dependency:io.micronaut.data:micronaut-data-nitrite-core[scope="annotationProcessor"]

NOTE: For Kotlin, add both dependencies to the `kapt` or `ksp` configuration, and for Groovy add both in `compileOnly` scope.

`micronaut-data-nitrite-core` is needed on the annotation processor path: it carries the `NitriteQueryBuilder` that ann:data.nitrite.annotation.NitriteRepository[] names, and Micronaut Data resolves that builder at compilation time. Without it, repository methods are compiled against the default JPQL query builder instead of into Nitrite filters, and Nitrite-specific features such as projections, association lookups and `$regex` queries are lost.

Then add a compile-scoped dependency on the Nitrite implementation:

dependency:io.micronaut.data:micronaut-data-nitrite[scope="implementation"]

=== Align Versions with the BOM

Import `io.micronaut.data:micronaut-data-nitrite-bom` to align the integration modules, Micronaut
Data and upstream Nitrite libraries. A BOM supplies dependency versions; choose the runtime modules
separately. In Gradle, import it on both the implementation and annotation processor configurations
when declaring versionless dependencies:

[source,groovy]
----
def nitriteVersion = "<nitrite-integration-version>"

dependencies {
    implementation platform("io.micronaut.data:micronaut-data-nitrite-bom:$nitriteVersion")
    annotationProcessor platform("io.micronaut.data:micronaut-data-nitrite-bom:$nitriteVersion")
    annotationProcessor "io.micronaut.data:micronaut-data-document-processor"
    annotationProcessor "io.micronaut.data:micronaut-data-nitrite-core"
    implementation "io.micronaut.data:micronaut-data-nitrite"
}
----

For Maven, import the BOM under `dependencyManagement` with `type=pom` and `scope=import`.
Declare the selected runtime artifact under `dependencies` and configure the annotation processor
path separately. Runtime dependencies do not automatically become annotation processors.

=== Choose Runtime Modules

All artifacts below use the group `io.micronaut.data`. Their published Maven POMs and Gradle
metadata include the dependencies shown, so consumers do not need to declare core or the upstream
adapter separately:

[cols="2,3",options="header"]
|===
|Artifact |Transitive dependencies
|`micronaut-data-nitrite` |Core plus the Micronaut MVStore integration; retains the default setup.
|`micronaut-data-nitrite-core` |Nitrite core and Micronaut Data runtime, document model and connection support.
|`micronaut-data-nitrite-mvstore` |Core plus `org.dizitart:nitrite-mvstore-adapter`, including its H2 dependencies.
|`micronaut-data-nitrite-rocksdb` |Core plus `org.dizitart:nitrite-rocksdb-adapter`, including RocksDB JNI and its serializers.
|`micronaut-data-nitrite-spatial` |Core plus `org.dizitart:nitrite-spatial`, including JTS and the geometry codec.
|===

For an in-memory application without storage adapters, use `micronaut-data-nitrite-core` on both
paths and set `micronaut.nitrite.default.storage-mode=IN_MEMORY`.

For RocksDB without MVStore, retain core on the annotation processor path and replace the runtime
`micronaut-data-nitrite` dependency with `micronaut-data-nitrite-rocksdb`. Configure `storage-mode`
and `db-path` as shown in <<nitriteConfiguration, Configuration>>. Add `micronaut-data-nitrite-spatial` alongside
the selected storage integration when using spatial queries; spatial itself does not select a
persistent store.

Jakarta Persistence and Jakarta Data APIs are compile-only dependencies of core. Applications using
those APIs directly should declare the corresponding API dependency explicitly.

The configuration properties and Java package names are unchanged. Adding only an upstream Nitrite
adapter does not install the Micronaut integration provider. Spatial excludes Jackson 3 databind;
its geometry codec does not require a Jackson JTS module.

== Saving an Instance (Create)

To save an instance use the `save` method of the `CrudRepository` interface:

snippet::example.BookRepositoryExample[project-base="doc-examples/nitrite-example", source="main", tags="save", indent="0"]

The `save` method inserts or updates according to what the collection holds:

- If the entity's ID is `null`, a new document is inserted and the ID is generated
- If the entity's ID is present in the collection, that document is replaced
- If the entity's ID is not present in the collection, a new document is inserted under it

This means `save()` can be used for both creating new entities and updating existing ones, including entities whose ID the application assigns itself.

== Native Images

The selected integration modules carry their backend metadata for GraalVM native images. Use the
same runtime dependencies for JVM and native applications.

This repository verifies core operations, MVStore/RocksDB persistence, transactions and spatial
queries in the dedicated Java/JUnit `data-nitrite-native-tests` project. With a GraalVM JDK selected
through `jenv`, compile and execute its native suite with:

[source,shell]
----
jenv exec ./gradlew :micronaut-data-nitrite-native-tests:nativeCheck
----

The default classpath includes all integrations. Append `-PnativeBackend=in-memory`, `mvstore`,
`rocksdb` or `spatial` to select an isolated classpath. This verification project is excluded from
publication and the consumer BOM; consumers select the integration libraries listed above. The
focused native suite complements the repository and Jakarta TCK suites run on the JVM.
